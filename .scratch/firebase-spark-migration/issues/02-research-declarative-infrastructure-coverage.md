# Establish declarative infrastructure coverage

Type: research
Status: resolved
Blocked by: none

## Question

Using primary provider documentation, determine which required Firebase, Google Cloud, GitHub, and Cloudflare resources can be managed declaratively without a billing account: project and Firebase enablement, Authentication providers and authorized domains, Firestore database/rules/indexes, Hosting sites and custom domains, DNS records, service identities, workload identity, secrets, and state storage. Classify each item as repository configuration, Terraform/OpenTofu-manageable, CLI-manageable, unavoidable manual bootstrap, or unsupported.

## Answer

Research current as of 2026-07-25. This is a documentation-based capability classification; no provider resources were created to test undocumented behavior.

### Result

Most of the destination can be repository-owned on Firebase Spark, but it cannot be one pure Terraform/OpenTofu graph:

- Google Cloud project creation, Firebase enablement, APIs, a Firebase Web App, Firestore, Hosting sites and custom domains, Cloudflare DNS, user-managed service accounts, service identities, and IAM bindings have Terraform resources.
- Firebase Authentication is the important split. The Google provider's Authentication resources require Identity Platform, and Firebase's Terraform guide requires a Blaze project for that provisioning path, so those resources are unusable under the Spark constraint. Identity Platform itself has a limited instrumentless Spark tier, but that does not make the Terraform path eligible. The Firebase CLI supports Google Sign-In as repository configuration in `firebase.json`, including OAuth brand data and redirect URIs, and deploys it with `firebase deploy --only auth` without documenting a Blaze requirement.
- Firestore rules and indexes, Hosting configuration and content, emulator configuration, and Auth provider configuration all have repository-owned Firebase CLI paths. Rules and indexes also have Terraform resources.
- Hosting provisions and renews its own certificate. Spark supports the `GROUPED` certificate type only. The certificate is observable but not independently managed.
- Cloudflare DNS is declarative, but Firebase computes the records it requires after the custom-domain resource exists. A Terraform shape therefore needs at least two phases or another reconciliation step.
- A safe shared state backend is possible without a Google or Cloudflare billing account through HCP Terraform Free, subject to its 500-managed-resource limit and account/token bootstrap. GCS Free Tier is not eligible because Google requires a Cloud Billing account; R2 requires an R2 subscription and bills overages. GitHub artifacts and caches are not state backends.
- Google WIF resources are declarative, but the official deployment-pipeline setup explicitly requires a billing-enabled Google Cloud project. WIF is therefore not established as usable under the strict no-billing constraint. CI can use Application Default Credentials, but the credential source still needs a separate decision.

### Manual boundary

The evidence supports keeping manual work to these bootstrap actions:

- Sign in to Google/Firebase, accept the Firebase Terms, and obtain local ADC.
- Sign in to Cloudflare and create the first narrowly scoped API token; inject it into the chosen CI secret store.
- If HCP Terraform is selected for state, create the free account/organization/workspace and bootstrap its local/CI token.
- If short-lived Google CI credentials cannot be made to work without billing, create and inject a least-privilege Google service-account key. This is supported but is a security compromise, not an architectural default.

OAuth provider configuration, Firestore, rules, indexes, Hosting, custom-domain reconciliation, DNS, deploys, emulator identities, and verification can all be repeatable repository commands after that boundary, except for the authorized-domain and WIF uncertainties called out above.

### Candidate shapes

These are capability shapes, not an architecture selection:

1. **Terraform plus Firebase CLI, with HCP Terraform state.** Terraform owns project/Firebase enablement, APIs, Web App, Firestore database, Hosting site/custom domain, Cloudflare DNS, identities, and IAM. Firebase CLI owns Auth, rules/indexes or only deployables, Hosting content, and emulators. HCP Free supplies shared state. This has the broadest declarative coverage but adds an HCP account/token and does not resolve Google CI credentials by itself.
2. **Repository scripts over Firebase/gcloud/Cloudflare APIs, without Terraform state.** Idempotent scripts query before creating or patching resources; checked-in Firebase config owns deployable concerns. This avoids state storage and can use identical local/CI commands, but the project/bootstrap scripts must implement drift detection, retries, import/adoption, and partial-failure recovery themselves. Authorized domains still need Spark verification.
3. **Local-only Terraform bootstrap plus recurring Firebase CLI deploys.** This avoids another state service but cannot honestly claim equivalent CI ownership of infrastructure. It is viable only if infrastructure changes are intentionally operator-local and CI is limited to validation and Firebase deployables; that tradeoff conflicts with the map's preference for equivalent workflows.

GCS and R2 state are not valid candidates under strict no-billing. GitHub artifacts/cache must not be used as substitutes.

### Risks and follow-up facts

- Firebase's Terraform support and the Hosting resources are beta. Pin provider versions and expect schema changes.
- Do not mix Firebase CLI and Terraform ownership for the same rules, indexes, site, or provider setting without an explicit import/handoff, or each tool can overwrite the other.
- The custom-domain flow is asynchronous and output-driven. Persist Firebase's ownership and CAA records; removing them can break future certificate issuance or renewal.
- Keep Cloudflare's Firebase records DNS-only until a hosted production test proves proxying is compatible with Firebase's host checks and certificate lifecycle.
- Before selecting WIF, run a non-provisioning support check or a disposable-project prototype specifically asking whether the IAM, STS, and Service Account Credentials APIs can support GitHub WIF with no Cloud Billing account attached.
- Before claiming full Auth automation, similarly prove an `authorizedDomains`-only Identity Toolkit PATCH against a standard Spark Firebase Auth project. Firebase's Terraform path is definitively disallowed under this map because that path requires Blaze; the direct API path is documented but its standard-Spark eligibility is not.
